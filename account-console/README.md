# OID4VP account console

The Keycloak account console, rebuilt from `@keycloak/keycloak-account-ui`, with one page of our
own: **Request a card**.

## Why a rebuilt console and not a theme

Keycloak's account console builds its routes from a **fixed array inside its own bundle**. A theme's
`content.json` can only *match* an existing route — `qN.find(r => r.path === (n.id ?? n.path))` in
26.7 — never create one. A custom entry with a concrete path therefore resolves to no element and
the page renders empty, with no error in the browser console.

Rebuilding the console is the supported answer, and the only one that yields a clean URL. See
<https://www.keycloak.org/ui-customization/creating-your-own-console>.

## Building

Everything runs in a pinned image; nothing touches a host toolchain. See
[`../docs/GETTING-STARTED.md`](../docs/GETTING-STARTED.md) for the full walkthrough.

```bash
docker build -f tools/account-console/Containerfile.node \
  -t keycloak-account-ui-build:1 tools/account-console/          # once

docker run --rm -v "$PWD":/src:z -w /src keycloak-account-ui-build:1 sh -c '
  cd account-console/oid4vp-account &&
  pnpm install --frozen-lockfile &&
  pnpm run notices &&
  pnpm run build &&
  mvn -B clean package -Dskip.installnodenpm=true -Dskip.npm=true'   # each time
```

Both commands are run from the repository root, and `podman` accepts them unchanged.

The result is `oid4vp-account/target/oid4vp-account-ui-0.1.0-SNAPSHOT.jar`, mounted into
`/opt/keycloak/providers/`. It carries the theme (`oid4vp`, type `account`), the front-end bundle,
and `META-INF/THIRD-PARTY-NOTICES.txt` — the attributions for everything the bundle inlines,
generated by `pnpm run notices` from the resolved dependency tree.

## Four traps, all silent, all paid for

**1. The package version must match the server.** The scaffold pins `26.5.x`; ours is pinned to the
server's `26.7.2`, because the console talks to the Account REST API of the server it is served by.

**2. Message bundles must ALSO be shipped under `theme-resources/messages/`.** Shipped only under
`theme/oid4vp/account/messages/`, they load when the theme comes from a directory but NOT
when it comes from a provider JAR — verified both ways on 2026-08-17. The menu then shows the raw
key (`cards`) instead of the label.

**3. `mvn clean`, not `mvn package`.** Without `clean`, Maven keeps the previous hashed bundle in
`target/classes` and the JAR ships two `main-*.js`. Both work, so nothing fails — the artifact just
doubles in size and stops telling you which build it is.

**4. Theme resources are cached by browsers for 30 days.** The URL carries a resource version tied to
the *Keycloak* version, not to the theme, so a redeploy is invisible to any browser that already
opened the console. During development, start the server with
`--spi-theme--static-max-age=-1 --spi-theme--cache-themes=false` (note the **double** dash between
the SPI name and the property; a single dash is silently ignored).

## Where things live

| Path | Role |
|---|---|
| `oid4vp-account/src/RequestCard.tsx` | Our page |
| `oid4vp-account/src/routes.tsx` | Routes — ours is **last**, which puts the tab at the bottom of the menu |
| `oid4vp-account/maven-resources/theme/oid4vp/` | Theme: `index.ftl`, properties, messages |
| `oid4vp-account/maven-resources/theme-resources/messages/` | The same messages, by the path that works from a JAR |

The page itself holds no business logic: it lists what `/realms/{realm}/cards/available` returns and
sends the holder to `/realms/{realm}/cards/request`, both served by the `oid4vp-login` extension,
which owns the rules and is covered by tests.
